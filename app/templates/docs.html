Page 1: Getting Started

1. Compilation & Installation Compile the project binaries from source:

cargo build --release

To run the server locally as a foreground process:

cargo run --release --bin maazdb-server

2. Automatic Secure Bootstrapping Upon first run, the server automatically checks for the presence of cryptographic identity assets inside the configured path (e.g., certs/server.crt and certs/server.key). If they are missing, MaazDB automatically generates a secure self-signed 10-year TLS certificate with Subject Alternative Names (SAN) pointing to localhost and 127.0.0.1 to ensure secure out-of-the-box driver handshake compatibility.

3. Connecting to the Database Connect to your local or remote instance using the command-line interface (CLI):

maazdb-cli

By default, the CLI reads persistent configurations. If none exist, it falls back to connection parameters 127.0.0.1:8888 using default administrative credentials.

Page 2: CLI Reference

The MaazDB CLI provides interactive management, configuration wizards, and real-time server diagnostics.

1. Interactive SQL Shell (REPL) Running maazdb-cli without any flags launches the interactive database shell.

  • Local Shell Intercepts: Control your client-side environment locally without issuing overhead server queries:
    • help : Prints the local help menu displaying REPL shortcuts.
    • clear : Instantly clears the terminal screen buffer.
  • Statement Execution: Terminate queries with a semicolon ; to send them to the server. You can write multi-line queries and include single-line comments (marked by --).
  • Script Support: Execute local SQL files sequentially using: sql SOURCE 'path/to/file.sql';

2. Intelligent Offline Recovery Fallback If a connection attempt fails, the CLI displays a context-aware fallback screen. You can interactively: 1. Launch the Configuration Wizard to adjust host, port, or user credentials. 2. Open the Server Performance Monitor to inspect local server process health. 3. Exit the application.

3. Interactive Configuration Wizard (--config / -c) Guide-driven setup for persistent connection parameters. Inputs are collected with masking on passwords for added terminal-level security.

4. Live Performance Monitor (--monitor / -m) A responsive TUI diagnostic dashboard that handles terminal resize events dynamically: * System Diagnostics: Global and per-core CPU and memory utilization. * Dedicated Process Telemetry: Diagnostics for maazdb-server (CPU, memory, virtual memory, disk read/write throughput, and runtime). * Network Activity: Linux socket tables tracking connection states, transaction bytes, and RX/TX throughput. * Storage Breakdown: Total database and table size metrics alongside local disk space warnings.

Page 3: SQL Reference

1. User Administration Commands MaazDB supports runtime credential management without requiring database server restarts.

CREATE USER Registers a new database user.

CREATE USER 'username' PASSWORD 'secure_password';

ALTER USER Changes the password for an existing user.

ALTER USER <username> IDENTIFIED BY '<new_password>';

DROP USER Removes a user account.

DROP USER 'username';

2. Advanced Ingestion Commands MaazDB supports optimized bulk writes directly in SQL.

Multi-Row Insert Inserts multiple rows of data in a single transactional query block to minimize network round-trips.

INSERT INTO users (name, age) VALUES 
('Alice', 30),
('Bob', 25),
('Charlie', 35);

INSERT INTO ... SELECT Enables high-performance data copying or archiving from one table schema directly into another.

INSERT INTO archived_users (name, score) 
SELECT name, score FROM active_players WHERE score > 1000;

3. Analytical Aggregates MaazDB supports standard SQL aggregations over visible MVCC transaction snapshots: * COUNT(*) : Count total matching records. * SUM(col) : Total the values of a numeric column. * AVG(col) : Calculate the mean of a numeric column. * MIN(col) : Find the lowest value. * MAX(col) : Find the highest value.

SELECT COUNT(*), AVG(salary), MAX(salary) FROM employees WHERE is_active = TRUE;

4. Point-in-Time Disaster Recovery Disaster recovery operations are exposed natively in the SQL dialect.

BACKUP Triggers a memory-table flush and writes a database snapshot to the specified folder directory.

BACKUP 'snapshot_v1';

SHOW BACKUPS Displays available backups stored in the storage root along with metadata, timestamp, and size.

SHOW BACKUPS;

RESTORE Overwrites the current database tables with data from the specified snapshot, replaying transaction log entries up to that moment.

RESTORE 'snapshot_v1';

1. Server Configuration (maazdb.toml) Server configurations are stored in an organized TOML file. If absent, a default file is created automatically on startup.

Default Locations: * Linux: ~/.config/maazdb/server/maazdb.toml * macOS: ~/Library/Application Support/maazdb/server/maazdb.toml * Windows: %APPDATA%\maazdb\server\maazdb.toml

Default Structure:

# MaazDB Server Configuration

[server]
host = "0.0.0.0"
port = 8888
cert_file = "certs/server.crt"
key_file = "certs/server.key"

[storage]
data_dir = "data"

[logging]
enabled = false
log_dir = "logs"
max_log_size_mb = 50
level = "info"

Default Locations: * Linux: ~/.config/maazdb/client/config.json * macOS: ~/Library/Application Support/maazdb/client/config.json * Windows: %APPDATA%\maazdb\client\config.json

Default Content:

{
  "host": "127.0.0.1",
  "port": 8888,
  "username": "admin",
  "password": "admin"
}

Page 5: Architecture

MaazDB is a columnar, disk-backed relational database engine designed for durability and low latency.

  • LSM Storage & Columnar Disk Structure:

    • LSM MemTable Cache: Intercepts write operations inside a fast BTreeMap transaction buffer, allowing high-frequency writes to complete with low latency.
    • Columnar Disk Storage: Checkpoints flush the MemTable sequentially to disk in individual column files (.bin files). This structure optimizes analytical queries by retrieving only the requested columns.
    • ChaCha20 Column Encryption: Protects data at rest by encrypting columnar pages natively.

  • MVCC Snapshot Isolation:

    • Lightweight Transaction Snapshots: Transactions operate on isolated snapshots. Read queries run concurrently without blocking write operations.
    • Atomic Rollbacks & Row-Level Locking: Handles updates and deletions cleanly via transactional version fields (xmin and xmax), securing records with row locks during active modifications.

  • Hybrid Primary Indexing & Sparse Indexing:

    • Root Map & Index Chunks: Uses a disk-backed, chunked index to handle large datasets. A root sparse index maps minimum keys to chunk IDs, loading target ranges into a small LRU chunk cache as needed.
    • Sparse Column Indices: Accelerates lookups in variable-length fields (such as TEXT and UUID) by mapping exact row positions to physical offsets in the column files, preventing expensive sequential table scans.

Part 2: Developer Documentation (DEVELOPER.md)

# MaazDB Developer Guide

Welcome, contributor! This document provides a deep dive into the internal architecture of MaazDB to help you get started.

## 1. Development Environment Setup

MaazDB uses a workspace architecture. For local development, compile the workspace and test interactions by running the local targets sequentially.

### Local Setup & Compilation
1. **Compile Workspace**:
   ```bash
   cargo build --release
   ```
2. **Launch Local Server**:
   ```bash
   cargo run --release --bin maazdb-server
   ```
3. **Execute Local CLI Client**:
   ```bash
   cargo run --release --bin maazdb-cli -- --config
   ```

All persisted configurations created via the local CLI will write to the default OS-specific standard folder under `maazdb/client/config.json`.

## 2. Core Architectural Philosophy

MaazDB is a multi-threaded, disk-backed, transactional database engine. Its design prioritizes:
1.  **Durability First:** Every insert, update, or delete is written to a Write-Ahead Log (WAL) and flushed before transaction commit.
2.  **Concurrency:** Multi-Version Concurrency Control (MVCC) permits lock-free reads alongside active writes.
3.  **Scalability:** Memory foot print is strictly controlled using a LRU-driven paged buffer pool.
4.  **Security:** Data-in-transit is secured via TLS 1.3, and data-at-rest is encrypted with ChaCha20.

## 3. Core Components Deep Dive

### SQLEngine (`src/sql/engine.rs`)
*   **Role:** The query routing and maintenance hub. It parses inbound commands, starts transaction IDs, manages sessions, and schedules core background routines.
*   **Background Maintenance Thread:** A background worker runs continuously on a 500ms sleep cycle to manage resources:
    1.  **WAL Fsyncing:** Flushes unwritten transaction buffers to physical disk every 500ms.
    2.  **Autonomous Checkpointing:** Truncates the active `wal.log` and checkpoints MemTable records to columnar storage when the WAL size exceeds 5MB or after a 5-second interval.
    3.  **Buffer Pool Purging:** Automatically unloads unused cache frames from memory if they have been idle for more than 60 seconds to optimize system resources.

### Columnar Storage & Buffer Pool (`src/storage/mod.rs`)
*   **Role:** Handles zero-copy reading and writing of database column files.
*   **BufferPoolManager:** Maintains page frames in memory.
    *   **Eviction:** Uses an LRU cache. When the pool reaches capacity, the least recently used clean page is evicted. If a page is dirty, it is encrypted and flushed before eviction.
    *   **In-Place Cryptography:** Employs ChaCha20 to secure data at rest. When writing to disk, a random 12-byte cryptographic nonce is generated and prefixed to the page. The rest of the page is encrypted in-place directly inside the page buffer to avoid memory copies. On page fetch, this process is reversed.

### Write-Ahead Log (`src/storage/wal.rs`)
*   **Role:** Guarantees durability and crash safety.
*   **Optimized Serialization:** Serializes transaction entries `(table, row)` using `bincode`. 
*   **Auto-Fsync:** Writes are buffered for performance and automatically flushed to disk when unflushed transaction logs exceed 1MB.
*   **Crash Recovery:** On database startup, the engine replays the `wal.log` sequentially, inserting recovered records into the in-memory MemTable to restore the database to its last consistent state.

### MemTable (`src/storage/memory.rs`)
*   **Role:** A high-speed, thread-safe memory buffer for incoming writes.
*   **TableData Rows:** Houses transactional versions of rows in a thread-safe `BTreeMap<u64, Arc<Row>>` protected by `parking_lot::RwLock`.
*   **MVCC-Aware Checkpointing:** During a checkpoint, `drain_table` is called to atomically clear the MemTable. All versions of rows are kept in order to prevent index offset drift.

### Primary Index (`src/storage/index_store.rs`)
*   **Role:** Speeds up primary key operations with O(1) direct access.
*   **Structure:** Chunks key-value pairs into sorted BTree files on disk (maximum 20,000 keys per chunk) to avoid large contiguous memory allocations.
*   **LRU Cache Control:** Loads active chunks into a small LRU cache (capped at 16 chunks to keep memory usage under 20MB), using an in-memory root map to route requests quickly.

## 4. Data Lifecycle (Write & Read Paths)

[WRITE PATH] SQL Statement -> SQLEngine -> Begin Tx -> Log to WAL -> Insert to MemTable -> Commit -> Success | (Background Thread) | Extract MemTable -> Flush to ColumnStore -> Update Index -> Truncate WAL

[READ PATH] SQL Statement -> SQLEngine -> Create Snapshot -> Primary Index (PK?) | +-------------+-------------+ | (Yes) | (No) Direct O(1) Vectorized Scan Point Lookup & Materialize | | +-------------+-------------+ | Apply MVCC Rules | Return Result Set


## 5. Areas for Contribution

*   **Analytical Features:** Additional SQL join methods (`JOIN`, `LEFT JOIN`), and extra filtering conditions.
*   **Query Optimization:** Cost-based index analyzers and vectorized query execution.
*   **Clustering & Distribution:** Implement the Gossip protocol and routing for replica setups.
